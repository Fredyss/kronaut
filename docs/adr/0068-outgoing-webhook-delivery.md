# ADR-0068: Outgoing webhook delivery

- **Status:** Accepted
- **Date:** 2026-11-26
- **Deciders:** Frederik Schlentc
- **Area:** Publishing pipeline, security
- **Spec:** [Publishing pipeline](../architecture/05-publishing-pipeline.md), [Security](../architecture/06-security.md), [Operations](../architecture/11-operations.md)
- **Extends:** [ADR-0031](0031-outgoing-webhooks.md) (signing and events)
- **Supersedes in part:** [ADR-0056](0056-least-privilege-global-tables-third-revision.md) (what `sweep_due_webhook_deliveries` returns), [ADR-0040](0040-idempotency-keys-for-every-write.md) (two routes that return a secret)

## Context

ADR-0031 fixes Standard Webhooks signing, the envelope and the event names. Phase 0 writes events and deliveries but sends nothing. The sender, the endpoint API and `webhook.test` need choices that receivers and stored rows depend on: the secret format, how a rotation overlaps, how a crashed send is picked up again, when retries stop, when an endpoint is turned off, and who may manage endpoints.

## Decision

**A cron task claims due deliveries through `sweep_due_webhook_deliveries`, signs each one per Standard Webhooks and posts it through egress. Owners and admins manage endpoints with a session; API keys never can.**

- **Secret:** `whsec_` plus the base64 of 32 random bytes, generated by the server and returned once, by create and by rotate. It is sealed in the envelope vault (ADR-0021) with AAD `endpoint id | workspace id | webhook_endpoint`; the current and the previous secret are always sealed together under one KEK, because the table has one `kek_version`.
- **Signing:** `webhook-id` is the event id, the same on every retry; `webhook-timestamp` is the send time in Unix seconds; `webhook-signature` is `v1,<base64 HMAC-SHA256 of id.timestamp.body>`. The body is the stored `payload` as Postgres renders it, so every attempt sends the same bytes.
- **Rotation:** the replaced secret becomes `previous_secret` for 24 hours, and deliveries in that window carry both signatures, newest first. Rotating again replaces the previous secret.
- **Claim:** inside the workspace, a claim sets `delivering`, counts the attempt and moves `next_attempt_at` 2 minutes ahead as a lease, then commits before the send. `sweep_due_webhook_deliveries` also returns `delivering` rows past their lease, so a crash mid-send is retried after the lease (migration 42). The finishing write is fenced by the attempt count. Delivery is at least once; receivers dedupe on `webhook-id`.
- **Outcome:** any 2xx is delivered. Anything else is a failed attempt with its HTTP status or the egress error code; the response body is never read or stored (`response_snippet` stays empty), and egress messages, which can name the URL, are never kept.
- **Retries:** after 1 min, 5 min, 30 min, 2 h, 5 h, 10 h and 10 h, so 8 attempts over about 28 hours; then the delivery is `dead`. No jitter: deliveries go out in the minute batches of the cron task.
- **Auto-disable:** a success resets `consecutive_failures` and `failing_since`. A failed attempt while `failing_since` is more than 5 days old disables the endpoint with reason `failing` and writes a system audit event. A claim for a disabled endpoint ends the delivery as `dead` with `endpoint_disabled`. Enabling it again clears the counters; dead deliveries are not resent.
- **Network:** user URLs go through `packages/egress`: `https` on port 443 only, no IP literals or credentials, every resolved address range-checked and the checked address used for the connection, no redirects, 15 s timeout, 1 MiB answer cap. The API refuses at save time what could never be delivered.
- **Management:** `/v1/workspaces/:workspaceId/webhooks` lists, creates, updates (URL, events, description, enabled), rotates, deletes and tests endpoints, with `auth: 'session'` and `webhooks:manage`, which only owners and admins hold and which is never grantable (ADR-0027). At most 20 endpoints per workspace. Audit events name the endpoint by id, never the URL, which can carry a token.
- **Idempotency:** create and rotate run outside `idempotency_keys`, because a stored response would keep the plaintext secret for 24 hours. A retried create makes a second endpoint and a retried rotate rotates again. Every other webhook write keeps its key.
- **`webhook.test`:** queues one event with empty `data` for the endpoint asked for only, whatever it subscribes to, at most 10 per endpoint per hour; it isn't subscribable. `post.approval_voided`, which the schema allows but ADR-0031 doesn't list, is neither subscribable nor emitted.
- **Retention:** events older than 30 days are deleted per workspace each day, and their deliveries with them.

## Options considered

- **Chosen:** the decision above.
- Rejected: a claim that writes `retry_wait` with the next retry time before the send, which would need no sweep change. It reports a live send as waiting and mixes the lease with the backoff.
- Rejected: keeping create and rotate idempotent and stripping the secret from the stored response. A replay would then return a response without the secret the first call already lost.
- Rejected: storing a response snippet. A receiver controls that body, so it could put anything into rows the UI shows.
- Rejected: letting API keys manage endpoints. An endpoint receives workspace events at a URL of the caller's choice, so it is a policy change.

## Consequences

- Receivers verify with any Standard Webhooks library and switch secrets without a gap.
- A crash between a send and its record resends that event once more after 2 minutes with the same id.
- A client that loses the response of a create or rotate has to rotate (again) to get a secret it knows.
- Revisit when: receivers need ordered delivery per endpoint, or a resend of dead deliveries is wanted.
